## Per-Engine Evaluation

### ganttEngine.js (549 lines)
The most complex engine in the system. Implements Kahn's topological sort (Step 1), a full CPM forward and backward pass (Steps 2–4), float calculation, and critical path identification. Additionally contains `calculateForecastOpening` (velocity-based re-forward-pass from actual data) and `recalculateOnDelay` (BFS propagation + backward pass). The engine is in excellent shape architecturally — pure JS, no React, no Supabase. Its two concerns (CPM scheduling and actuals-based forecasting) are arguably tightly related enough that housing them together is defensible, though a `forecastEngine.js` extraction could reduce file length. The internal `addDays` / `diffDays` are also present in `ganttLayout.js` — minor duplication.

### ganttLayout.js (339 lines)
Pure geometry engine. Converts the CPM result into pixel coordinates for SVG rendering. Single responsibility: layout mathematics. `generateArrowPath` is the most algorithmically interesting piece — it routes arrows below bars when the successor starts before the predecessor finishes. No test coverage. Since it deals only with presentation math, business risk is low, but a visual regression test suite would be valuable.

### progressEngine.js (373 lines)
Declared "Single source of truth for all progress calculations" and largely lives up to it. The three-level API (activity → phase → project) is clean. `calculateProgressComparison` stretches the file by mixing schedule comparison and SPI computation with progress math, but these are logically adjacent. The key concern: `calculateProgressComparison` computes `expectedPct` identically to `riskEngine.computeScheduleDeviation`. This is a latent divergence risk — one thresholds get tweaked, the other doesn't.

### evmEngine.js (88 lines)
Small and focused. Computes EV/PV/SPI/EAC/TCPI correctly. Correctly delegates `computeScheduleDeviation` to riskEngine rather than re-implementing it. However, the SPI formula at line 41 (`EV/PV`) is conceptually identical to spiEngine's `sumActual/sumPlanned` — they differ only in input granularity (report-level vs task-row-level). This is acceptable but should be documented.

### riskEngine.js (447 lines)
The risk-scoring engine is well-structured with all weights externalised to `riskWeights.js`. The largest single concern: `expectedPct` is calculated inline at line 187-189 (inside `computeProjectRiskScore`) using the same formula as `progressEngine.calculateProgressComparison` and `riskEngine.computeScheduleDeviation`. This is the most prominent Source-of-Truth violation in the codebase — the expectedPct formula appears in three distinct locations within this file's own ecosystem. The SPI inline calculation at lines 242-254 is explicitly commented as avoiding a circular import — this is the correct trade-off given the circular dep would be worse, but it is still a code smell.

### spiEngine.js (68 lines)
Focused, clean, well-commented. The stale-Gantt guard (returning null when `sumActual===0 && avgPlanned>=80`) prevents false critical SPI readings. Correctly extracted from `ganttService.js` for testability. The only concern is the conceptual overlap with evmEngine — both compute SPI but from different data sources (Gantt DB rows vs report-level progress).

### contractorDriftEngine.js (185 lines)
Well-designed. Correctly delegates per-item comparison to `pmAlignmentEngine` rather than reimplementing it. The three pattern classifications (systematic_overstatement, panic_report, front_loading) are crisp with documented thresholds. No test coverage.

### pmAlignmentEngine.js (208 lines)
Handles two report formats (legacy column-based and new WP format) through auto-detection. `computeConfidenceLevel` is well-designed — points-based scoring with clear breakdown. The multi-format support is necessary but increases cognitive complexity.

### portfolioEngine.js (134 lines) — AD-004 CLOSED
Split in commit `dbd3345`. Now contains only portfolio-level alert/KPI/contractor/missing-report functions (5 exports). Previously duplicated `computeExpectedPct` inline is now resolved (AD-001). SRP is satisfied. The site-visit and risk-summary concerns live in their own files (see siteVisitEngine.js, portfolioRiskEngine.js below).

### siteVisitEngine.js (115 lines) — new (AD-004)
Focused on PM vs GC site-visit comparison. Handles the 3-format detection (Gantt WP / legacy WP / flat fields) cleanly. Uses `classifyDiscrepancy` from discrepancyEngine (AD-005) for consistent classification. Remaining concern: 3-format structural detection is still duplicated in `projectSummaryEngine.js` — partially addressed by classifyDiscrepancy unification, but the format branching code still appears twice. No test coverage yet.

### portfolioRiskEngine.js (23 lines) — new (AD-004)
Minimal and clean. `computeRiskSummaryStats` is entirely self-contained (no imports). No test coverage needed at this size; every branch is trivially exercised by any non-empty portfolio. `computeSpiAlerts` was deleted (commit `efe41a2`) after confirming zero importers in the codebase.

### contractorEngine.js (112 lines)
Scoring engine with 5 weighted dimensions. Line 52-54 recalculates project progress (`computeWPCumulativeStatuses` + `calculateProjectProgressResult`) independently of the `progress` value already computed by `useAllRows`. This is a minor redundancy: `contractorEngine` could accept `progress` as a parameter.

### openingReadinessEngine.js (124 lines)
Clean, focused, data-driven. Reads blocker definitions from `workPackages.js` config rather than hardcoding task names. Returns structured status with reasons array. Correctly used by commandEngine as a pre-computed input.

### commandEngine.js (157 lines)
Exemplary engine design. Explicitly documented: "Does NOT recalculate anything." Consumes pre-computed outputs from five other engines. All thresholds come from `scheduleConfig.js` config. Output sorted by severity. The closest thing to perfect SRP in the codebase.

### escalationEngine.js (79 lines)
Small and clean. Four distinct escalation conditions (A–D) with clear severity logic. Correctly delegates mismatch detection to pmAlignmentEngine.

### actionEngine.js (42 lines)
Very small. Returns max 3 prioritised actions. Conceptually overlaps with `commandEngine.js` — both produce "what the PM should do" outputs. The difference: commandEngine produces structured Commands (for the Home page priorities feed), actionEngine produces a simpler action list (for Risk Dashboard CRITICAL/HIGH cards). The overlap is a product decision that should be documented and potentially unified.

### projectHealthEngine.js (76 lines)
Simple compositing engine. Takes three pre-computed scores and combines them with fixed weights (riskPts 30%, progressPts 25%, contPts 20%, alignPts 15%, pmPts 10%). The weights are hardcoded — should be externalised to config to match the pattern established by riskWeights.js.

### projectSummaryEngine.js (203 lines)
Utility engine for the ProjectDetailDrawer. Contains a `pmVisit` section (lines 85-159) that reimplements PM visit statistics (assessed/matches/discrepancies/pmAhead) also present in `portfolioEngine.computeSiteVisitData`. The two implementations handle the same three-format detection (Gantt WP, legacy WP, oldest flat) with slightly different branching — a maintenance hazard.

### cascadeEngine.js (188 lines)
Well-factored. BFS propagation, terminal WP detection, and cascade depth tracking. Explicitly avoids duplicating the topological sort from ganttEngine. One concern: `detectCurrentDelays` at line 160 recomputes expectedPct per WP (line 177) using elapsed/duration — conceptually similar to spiEngine's `computePlannedPct` but not sharing the function.

### discrepancyEngine.js (111 lines)
Small and correctly scoped. The `discrepancyStatus` thresholds (10 = warning, 25 = critical) are hardcoded — should be configurable. `mergeDiscrepanciesIntoGantt` is a pure merge function.

### monteCarloEngine.js (131 lines)
Correct use of Box-Muller for normal random variates. 10,000-simulation ceiling. Depends on `progressAtIndex` to reconstruct weekly progress series from reports — this means Monte Carlo is sensitive to the same cumulative-status logic as the main progress display. The 520-week MAX_WEEKS cap prevents infinite loops on stalled projects. No test coverage for a stochastic engine is a gap — at minimum, a deterministic smoke test with a fixed seed would be valuable.

### progressDeltaEngine.js (134 lines)
Handles two related concerns: per-task delta computation between consecutive report dates, and phase classification (done/current/upcoming). These are often used together but are conceptually distinct operations. `phasePct` at line 56 mirrors `PhaseStepper.wpProgress` logic — a known duplication acknowledged in the file comment.

### permissionEngine.js (22 lines)
Trivially thin wrapper over the rolePermissions config. Correct pattern for permission lookups. No business logic.
